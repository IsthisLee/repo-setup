# 0007. 설명 카드로 두 번 확인받고 변경은 브랜치와 PR 로 올린다

- 상태: 승인 (2026-09-22)

## 맥락

이전 진입점은 용도가 모호하거나 되돌리기 어려운 항목이 섞일 때만 사용자에게 확정을 받았다. 파일을 쓰기
전에 확인하는 자리가 없었고, 처음 보는 사람이 읽고 결정할 수 있는 설명 형식도 없었다. 그래서 사용자는
무엇에 동의하는지 모른 채 세팅이 진행되었다.

이미 개발 중인 저장소에 얹을 때도 정해진 것이 없었다. 변경을 기본 브랜치에 바로 커밋하는지, 브랜치 보호가
열린 PR 과 자동화에 어떤 영향을 주는지를 사용자가 미리 알 방법이 없었다.

## 결정

확인을 두 층으로 받는다. 먼저 실측 결과와 함께 목적마다 설명 카드를 보이고 적용할 목적을 고르게 한다.
그다음 고른 목적 안에서 부작용이 있는 단계(파일 쓰기, 푸시, GitHub 설정 바꾸기, 로컬 테스트 실행)마다
다시 확인받는다. 카드는 무엇, 이유, 바뀌는 것, 겪는 일, 감수할 것, 되돌리기, 건너뛰면의 일곱 칸이고, 문구는
각 목적의 `PROCEDURE.md` 에 둔다.

변경은 기본 브랜치에 직접 커밋하지 않는다. 작업 트리에 커밋하지 않은 추적 파일의 변경이 없을 때만 시작하고,
기본 브랜치의 최신 상태에서 세팅 브랜치를 만들어 목적마다 커밋한 뒤 PR 한 개로 올린다. 파일과 무관한 GitHub
설정은 확인을 받은 뒤 바로 바꾸고, 브랜치 보호는 세팅 PR 이 병합된 뒤에 건다.

## 결과

- 사용자는 켠 뒤 겪을 일과 되돌리는 법을 읽고 목적을 고른다. 카드의 숫자는 그 저장소에서 잰 값이다.
- 모든 파일 변경이 PR 리뷰를 거치고, PR 한 개가 되돌릴 단위가 된다. 목적마다 커밋이 나뉘어 있어 리뷰에서
  목적별로 볼 수 있다.
- 확인 질문이 늘어난다. 목적을 고르는 질문이 두 번(Claude Code 의 `AskUserQuestion` 은 질문 한 개에
  선택지를 네 개까지 받는다), 부작용이 있는 단계마다 한 번씩이다.
- 브랜치 보호는 세팅 PR 이 병합되기 전까지 걸리지 않는다. 필수로 걸 검사를 만드는 워크플로가 기본 브랜치에
  없을 때 걸면 다른 PR 이 모두 멈추기 때문이다. 그래서 `contrib` 은 병합한 뒤 한 번 더 불러야 끝난다.
- 커밋하지 않은 변경이 있는 저장소에서는 시작하지 않는다. 세팅 커밋에 남의 변경이 섞이지 않는 대신, 사람이
  먼저 정리해야 한다.
- 카드 문구의 정본은 절차 문서 하나다. 진입점은 채우는 규칙만 갖고 문구를 옮겨 적지 않는다.
