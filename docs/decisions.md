# 설계 결정: 왜 좁은 스킬 다섯으로 나눴나

이 문서는 `repo-setup` 이 무엇을 책임지고 무엇을 책임지지 않는지, 그리고 그 경계를 왜 그렇게
그었는지를 적습니다. 스킬을 더하거나 뺄 때 여기를 먼저 읽고 고칩니다.

## 한눈에 보기

| 스킬 | 소유하는 것 | 성공 판정 | 순서 |
|---|---|---|---|
| `repo-privacy` | 커밋 훅, 패턴 출처 셋, `core.hooksPath`, `.gitignore` 의 `.private/` 한 줄 | 홈 경로가 든 커밋이 실제로 막힌다 | 1 |
| `repo-license` | `LICENSE`, 매니페스트의 `license` 필드, SPDX 헤더 | 파일과 매니페스트가 같은 라이선스를 말한다 | 2 |
| `repo-ci` | 테스트 워크플로 파일, 매트릭스 | 워크플로가 실제로 한 번 돌아 통과한다 | 3 |
| `repo-secure` | secret scanning, push protection, 코드 스캐닝, `dependabot.yml`, 액션 SHA 고정, 토큰 권한 | GitHub API 가 `enabled` 를 돌려준다. 워크플로에 태그 참조가 없다 | 4 |
| `repo-contrib` | CONTRIBUTING, 이슈·PR 템플릿, CODEOWNERS, `SECURITY.md`, 브랜치 보호 | 파일이 놓였다. 보호 규칙 API 응답이 맞다 | 5 |

## 1. 책임 범위는 저장소 층이다

**git 과 GitHub 에 속하는 것만 다룹니다.** 린터, 포매터, 테스트 러너, 빌드 설정 같은 언어별
도구 체인은 다루지 않습니다.

- 이 경계를 그은 이유는 **검증 방법이 일관되기 때문**입니다. 저장소 층은 파일을 놓았는지, 훅이
  실제로 막는지, GitHub API 가 무엇을 돌려주는지로 전부 판정됩니다. 언어가 섞이면 스킬마다
  검증 수단이 달라지고, 검증할 수 없는 스킬이 생깁니다.
- 도구 체인은 이미 `npm create`, `uv init`, 프레임워크 CLI 가 하는 일입니다. 우리가 다시 만들면
  그것들과 어긋나고 낡습니다.
- 사용자 전역 규칙에 「설정 파일은 작업 대상일 때만 수정한다」가 있어, 도구 체인을 건드리는
  스킬은 그 규칙과 충돌합니다.

## 2. 자르는 단위는 목적이다

같은 항목을 항목별(아홉 개), 층별(세 개), 목적별(다섯 개)로 자를 수 있었습니다. **목적별을
골랐고, 기준은 「묶음마다 검증 방법이 하나씩일 것」입니다.**

좁은 스킬을 나눈 원래 이유가 각자 테스트로 지키기 위해서였습니다. 검증 방법이 같은 것끼리
묶으면 그 스킬의 테스트가 한 종류로 끝납니다.

- **항목별 아홉 개를 버린 이유**: 전역 이름 공간에 `repo-` 로 시작하는 스킬이 열 개 넘게 깔리고,
  진입점이 매번 열 개를 순회해야 하며, 서로 의존하는 것(브랜치 보호는 CI 가 있어야 의미가
  있습니다)을 조율할 자리가 없어집니다.
- **층별 세 개를 버린 이유**: 「파일을 놓는 것」 한 묶음에 라이선스부터 CONTRIBUTING 까지 일곱
  가지가 들어가 이것저것 담긴 큰 문서가 됩니다. `did-you-check` 에서 `PUBLIC-REPO-GUARD.md` 를
  지운 것과 같은 실패입니다.

## 3. 경계에서 부딪히는 곳 셋

**`.github/workflows/*.yml` 을 둘이 건드립니다.** `repo-ci` 가 파일을 만들고, `repo-secure` 는
이미 있는 파일의 액션 고정과 `permissions` 만 고칩니다. 그래서 `repo-ci` 가 먼저입니다. CodeQL
워크플로는 `repo-secure` 가 자기 파일(`codeql.yml`)로 따로 만듭니다.

**브랜치 보호는 `repo-contrib` 이 갖습니다.** 검증 방법은 `repo-secure` 와 같은 API 호출이지만,
혼자 쓰는 저장소에는 의미가 없는 협업 장치라서 목적 쪽을 따랐습니다.

**`.gitignore` 전체는 어느 스킬도 갖지 않습니다.** 언어마다 내용이 달라 저장소 층을 벗어나고,
이미 `gitignore.io` 와 각 프레임워크 CLI 가 하는 일입니다. 다만 `.private/` 를 무시하는 줄은
가드의 일부이므로 `repo-privacy` 가 그 한 줄만 책임집니다.

## 4. 진입점의 판단 규칙

### 실측은 공통과 스킬별로 나눈다

여러 스킬이 함께 쓰는 것만 진입점이 잽니다. 한 스킬만 쓰는 것은 그 스킬이 잽니다. 그러지 않으면
해당하지 않는 저장소에서도 매번 전부 돌게 됩니다.

| 층 | 재는 것 |
|---|---|
| 공통(진입점) | 공개 여부, 소유(개인·팀), 호스트, 기존 훅 관리자, 기본 브랜치 이름 |
| 스킬별 | 테스트 명령(`repo-ci`), 매니페스트의 `license` 필드(`repo-license`), 기존 워크플로의 액션 참조 방식(`repo-secure`) |

기본 브랜치 이름을 공통에 올린 이유는 `repo-ci`·`repo-secure`·`repo-contrib` 셋이 쓰기 때문입니다.

### 실측값에서 스킬을 고른다

| 스킬 | 고르는 조건 | 빼는 조건 |
|---|---|---|
| `repo-privacy` | 항상 | 없음. 남의 훅 관리자가 잡고 있으면 덮지 않고 공존 한 줄을 안내한다 |
| `repo-license` | `LICENSE` 가 없고 공개이거나 배포물이다 | 비공개 개인 실험 |
| `repo-ci` | 테스트 명령이 실측되고 워크플로가 없다 | 테스트가 없으면 만들지 않는다 |
| `repo-secure` | 호스트가 GitHub 다 | 권한이 없으면 제안만 한다 |
| `repo-contrib` | 공개이고 기여를 받거나 팀 저장소다 | 개인 비공개 |

**테스트가 없는 저장소에 CI 를 만들지 않습니다.** 빈 CI 는 아무것도 검사하지 않으면서 통과
표시만 줍니다. 그 표시를 믿고 브랜치 보호의 필수 검사로 걸면 보호가 껍데기가 됩니다.

### 호출 순서와 그 근거

`repo-privacy` → `repo-license` → `repo-ci` → `repo-secure` → `repo-contrib`

- 가드가 맨 앞입니다. 뒤 단계가 만드는 파일도 가드를 거쳐야 합니다.
- `repo-ci` 가 `repo-secure` 보다 앞입니다. 3절의 파일 소유 관계 때문입니다.
- `repo-contrib` 이 맨 뒤입니다. 브랜치 보호에 CI 상태 검사를 필수로 걸려면 CI 가 먼저 있어야
  합니다.

## 5. 다섯이 공유하는 규칙 둘

**팀 저장소면 공유 자산을 고치지 않고 제안만 합니다.** `repo-secure` 와 `repo-contrib` 은 팀
저장소에서 대부분 권한이 없어 실패합니다. 그 실패를 결함으로 보고하지 않고 「권한이 없어 제안만
한다」로 처리합니다.

**스킬 본문은 자기 폴더만으로 완결됩니다.** `npx skills` 는 스킬 폴더만 가져가므로 부모 폴더를
가리키면 깐 쪽에서 그 파일이 없습니다. 다만 **폴더 안의 하위 파일은 함께 복사되고 실행 비트도
보존됩니다.** CLI 1.7.0 으로 직접 확인했습니다(2026-09-22). 그래서 템플릿은 본문에 인용하지 않고
`<스킬>/templates/` 에 실제 파일로 둡니다.

## 6. 기존 두 스킬에서 고칠 것 넷

1. **진입점의 「목록에 없는 세팅은 보고만 한다」 문단을 고칩니다.** 그 문단의 예시가 라이선스,
   CI, 브랜치 보호인데 셋 다 목록에 들어옵니다. 규칙은 남기고 예시를 바꿉니다. 이 문단이 스킬이
   하나뿐이던 동안 진입점이 아무것도 하지 못한 직접 원인입니다.
2. **3절 표의 「상태」 칸을 「순서」와 「선행」으로 바꿉니다.** 다섯이 다 있으면 「있음」은
   정보가 아닙니다.
3. **`repo-privacy` 의 템플릿 인용 146줄을 실제 파일로 뺍니다.** 5절의 실측이 근거입니다. 294줄이
   약 150줄로 줄고 부르는 비용이 줍니다. 정본을 스킬 폴더로 옮기고 저장소 루트의 `templates/` 를
   없앱니다. 같은 내용이 두 곳에 있던 것이 사라지므로 「템플릿 인용 대조」 검사도 없어집니다.
4. **훅 템플릿에 박힌 `did-you-check` 고유 경로를 일반화합니다.** `case` 문의
   `docs/superpowers/`, `docs/design-plan-review*` 는 남의 저장소에서 무의미합니다.
5. **`repo-privacy` 의 서버 층 단계를 `repo-secure` 로 옮깁니다.** 1절의 소유 표에서 secret
   scanning 은 `repo-secure` 의 것입니다. 옮긴 뒤 `repo-privacy` 는 단독으로 불렸을 때
   호스트 층이 아직 안 켜졌을 수 있다는 사실을 보고합니다.

## 7. 일부러 하지 않는 것

- **언어별 도구 체인**(1절). 범위 밖입니다.
- **`.gitignore` 전체**(3절). `.private/` 한 줄만 다룹니다.
- **항목별로 더 잘게 쪼개기**(2절). 필요해지면 그때 나눕니다.
- **스킬을 한 번에 만들기.** 검증 방법이 제각각이라 하나씩 만들고 각각 테스트를 붙였습니다.
  다섯이 모두 들어온 뒤에도 이 원칙은 유지합니다. 여섯째를 더할 때도 그렇게 합니다.
